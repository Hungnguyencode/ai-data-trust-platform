# Scoring Method and Decision Logic

## 1. Purpose

This document explains how **AI-assisted Data Trust Platform** evaluates dataset trustworthiness and how the different analytical signals relate to governance.

The platform deliberately separates several concepts that are easy to confuse:

```text
Data Trust Score
Privacy Risk
Drift Evidence
Freshness
Volume Monitoring
Validation Gate
Governance Decision
Lifecycle State
```

They are related, but they are not the same thing.

The current Data Trust Score is a weighted score built from five components:

```text
Completeness
Validity
Uniqueness
Consistency
Anomaly Safety
```

Privacy Risk is evaluated separately and is used directly by Governance.

Drift, Freshness, Volume Monitoring, Data Contracts, and pipeline operational status are also separate evidence streams.

---

## 2. Single Source of Truth

The main implementation is:

```text
src/scoring/score_engine.py
```

with weights defined in:

```text
src/scoring/weights.py
```

The FastAPI score endpoint does not maintain a second scoring implementation.

The API calls the same core function used elsewhere:

```python
calculate_data_trust_score(...)
```

This is an important design property:

```text
same dataset
+ same quality evidence
= same scoring engine
```

The goal is to prevent the UI, API, tests, and orchestration code from drifting into different scoring rules.

## 3. Overall Formula

The current component weights are:

| Component | Weight |
|---|---:|
| Completeness | 0.25 |
| Validity | 0.25 |
| Uniqueness | 0.20 |
| Consistency | 0.15 |
| Anomaly Safety | 0.15 |
| **Total** | **1.00** |

The overall score is:

```text
Overall Score
=
Completeness × 0.25
+ Validity × 0.25
+ Uniqueness × 0.20
+ Consistency × 0.15
+ Anomaly Safety × 0.15
```

All component scores are clamped to:

```text
0 <= score <= 100
```

and rounded to two decimal places.

The weight configuration is validated before the final score is calculated. If the weights no longer sum to `1.0`, the scoring engine raises an error instead of silently producing a misleading score.

---

## 4. Completeness Score

Completeness measures how much of the dataset is populated rather than missing.

Let:

```text
total_cells = number_of_rows × number_of_columns
missing_cells = total number of null / missing cells
```

Then:

```text
missing_rate = missing_cells / max(total_cells, 1)
```

and:

```text
Completeness Score = 100 × (1 - missing_rate)
```

Example:

```text
1,000 total cells
50 missing cells

missing_rate = 50 / 1000 = 0.05
Completeness = 100 × (1 - 0.05)
             = 95
```

Interpretation:

```text
higher score
= fewer missing values
```

The `raw_value` stored for this component is the missing percentage.

---

## 5. Uniqueness Score

Uniqueness currently evaluates fully duplicated rows.

Let:

```text
total_rows = number of rows
duplicate_rows = number of rows marked duplicated by pandas
```

Then:

```text
duplicate_rate = duplicate_rows / max(total_rows, 1)
```

and:

```text
Uniqueness Score = 100 × (1 - duplicate_rate)
```

Example:

```text
1,000 rows
20 duplicate rows

duplicate_rate = 20 / 1000 = 0.02
Uniqueness = 100 × (1 - 0.02)
           = 98
```

Interpretation:

```text
higher score
= fewer fully duplicated rows
```

This is currently a row-level duplicate check. It is not yet a full business-key uniqueness engine.

---

## 6. Validity Score

Validity uses issues generated by the quality-rule engine.

The current validity-related issue types are:

```text
Invalid Numeric Type
Invalid Datetime Type
Invalid Range
Invalid Age Range
Invalid Categorical Value
```

The engine first calculates:

```text
invalid_count
=
sum(issue_count for validity-related issues)
```

Then:

```text
total_cells = max(rows × columns, 1)

invalid_rate = invalid_count / total_cells
```

The current penalty is intentionally stronger than a one-to-one percentage deduction:

```text
penalty = invalid_rate × 100 × 3
```

Therefore:

```text
Validity Score = 100 - penalty
```

or equivalently:

```text
Validity Score = 100 - (invalid_rate × 300)
```

The result is clamped to `[0, 100]`.

Example:

```text
10,000 cells
100 validity errors

invalid_rate = 100 / 10,000 = 0.01

penalty = 0.01 × 100 × 3
        = 3

Validity Score = 97
```

If no quality issues are present, Validity is returned as:

```text
100
```

Interpretation:

```text
higher score
= values are more compliant with expected type,
  format, range, and categorical rules
```

---

## 7. Consistency Score

Consistency currently focuses on formatting consistency and applies a smaller secondary penalty for missing values.

The explicit consistency issue type is:

```text
Text Format Inconsistency
```

The engine calculates:

```text
consistency_error_count
=
sum(issue_count for Text Format Inconsistency)
```

Missing values are then added with half weight:

```text
weighted_error_count
=
consistency_error_count
+ 0.5 × missing_count
```

The error rate is:

```text
error_rate
=
weighted_error_count / total_cells
```

The penalty is:

```text
penalty = error_rate × 100 × 2
```

Therefore:

```text
Consistency Score = 100 - penalty
```

or:

```text
Consistency Score = 100 - (error_rate × 200)
```

The result is clamped to `[0, 100]`.

Why is missingness only multiplied by `0.5` here?

Because missingness already has its own first-class component:

```text
Completeness
```

Without the reduced coefficient, the same problem would be punished too aggressively in both components.

---

## 8. Anomaly Safety Score

The Trust Score does not use a single outlier detector.

The anomaly engine combines evidence from:

```text
IQR
Z-score
Isolation Forest
```

The union of all detected row indexes is used:

```text
combined anomaly rows
=
IQR rows
UNION
Z-score rows
UNION
Isolation Forest rows
```

This avoids counting the same row multiple times simply because several methods detect it.

Let:

```text
total_anomaly_rows
=
number of unique combined anomaly rows
```

Then:

```text
anomaly_rate
=
total_anomaly_rows / total_rows × 100
```

The current anomaly score formula is:

```text
Anomaly Safety Score
=
100 - (anomaly_rate × 2)
```

The result is clamped to `[0, 100]`.

Example:

```text
5% of rows are classified as anomaly

Anomaly Safety Score
= 100 - (5 × 2)
= 90
```

This means the anomaly component deliberately applies a relatively strong penalty.

---

## 9. IQR Detection

For each numeric column, the engine calculates:

```text
Q1 = 25th percentile
Q3 = 75th percentile
IQR = Q3 - Q1
```

A value is treated as an IQR outlier when:

```text
value < Q1 - 1.5 × IQR
```

or:

```text
value > Q3 + 1.5 × IQR
```

Columns with fewer than four non-null observations are skipped.

If:

```text
IQR = 0
```

the column does not produce IQR outliers in the current implementation.

---

## 10. Z-score Detection

For each numeric column:

```text
z = (x - mean) / standard_deviation
```

The default threshold is:

```text
abs(z) > 3.0
```

Columns with fewer than four non-null observations are skipped.

Columns with zero standard deviation are also treated as having no Z-score outliers.

---

## 11. Isolation Forest

The Isolation Forest implementation uses numeric columns only.

Before model inference:

```text
missing numeric values
→ median imputation
→ StandardScaler
→ Isolation Forest
```

Current defaults:

```text
contamination = 0.1
random_state = 42
n_estimators = 100
```

Isolation Forest is not used when:

```text
there are no numeric columns
```

or:

```text
dataset has fewer than 8 rows
```

This prevents a model from pretending to produce useful anomaly evidence when the dataset is too small.

---

## 12. Anomaly Risk Level

The anomaly engine also exposes its own risk classification.

| Anomaly Safety Score | Risk |
|---:|---|
| `>= 90` | Low |
| `>= 75` | Medium |
| `>= 50` | High |
| `< 50` | Critical |

This risk label belongs to the anomaly subsystem.

It should not be confused with the overall Data Trust Score risk label, whose thresholds are slightly different.

---

## 13. Overall Trust Risk Level

After the weighted score is calculated, the platform classifies it as:

| Overall Data Trust Score | Risk Level |
|---:|---|
| `>= 85` | Low |
| `>= 70` | Medium |
| `>= 50` | High |
| `< 50` | Critical |

The label describes the current rule-based interpretation of the score.

It is not a statistical probability of failure.

---

## 14. AI Readiness

The current Data Trust Score is also mapped to an AI-readiness message.

| Overall Score | AI Readiness |
|---:|---|
| `>= 85` | Ready for Analytics and ML |
| `>= 70` | Usable, Minor Cleaning Needed |
| `>= 50` | Needs Cleaning Before Training |
| `< 50` | Not Ready for AI/ML |

This is a project-level operational interpretation.

It should not be presented as a universal industry standard.

A dataset can score highly and still require business-specific validation before production ML use.

## 16. Important: Privacy Is Not Inside the Trust Score

The current Trust Score weights are only:

```text
Completeness
Validity
Uniqueness
Consistency
Anomaly Safety
```

Privacy is deliberately evaluated separately.

This distinction is important.

A dataset can have:

```text
high Data Trust Score
```

while still containing:

```text
Email
Phone Number
Citizen ID
Full Name
Address
```

Therefore:

```text
high quality
!=
safe to publish
```

Privacy evidence enters the Governance Engine directly.

---

## 17. Privacy Safety Score

The Privacy scanner detects several PII categories using regular expressions and/or column-name heuristics.

Current categories include:

```text
Email
Phone Number
Citizen ID
Full Name
Address
```

Each finding has a severity.

The current severity weights used for the Privacy Safety Score are:

| Severity | Weight |
|---|---:|
| Low | 0.6 |
| Medium | 1.0 |
| High | 1.8 |
| Critical | 2.5 |

For all findings:

```text
weighted_risk
=
Σ(match_count × severity_weight)
```

Then:

```text
risk_rate
=
weighted_risk / total_cells
```

and:

```text
Privacy Safety Score
=
100 - risk_rate × 100
```

The result is clamped to `[0, 100]`.

If no PII finding exists:

```text
Privacy Safety Score = 100
```

---

## 18. Privacy Risk Level

Privacy uses:

| Privacy Safety Score | Risk |
|---:|---|
| `>= 90` | Low |
| `>= 75` | Medium |
| `>= 50` | High |
| `< 50` | Critical |

Again, this is separate from the Data Trust Score.

---

## 19. PII Severity Rules

High-risk PII categories currently include:

```text
Citizen ID
Phone Number
Email
```

For Email and Phone:

```text
match_rate >= 20%
→ High

otherwise
→ Medium
```

Citizen ID findings are currently assigned:

```text
High
```

Full Name and Address use:

```text
match_rate >= 30%
→ High

otherwise
→ Medium
```

These are deterministic portfolio rules rather than claims of legal compliance.

---

## 20. Governance Is the Final Decision Layer

The Data Trust Score itself does not approve a dataset.

The Governance Engine combines:

```text
Validation status
blocking issue count
Data Trust Score
Privacy Risk
```

The default Trust Score threshold for governance is:

```text
70
```

The Governance Engine returns one of:

```text
APPROVED
REVIEW_REQUIRED
REJECTED
```

---

## 21. Governance Decision Order

The current decision flow is effectively:

```text
if Validation != ACCEPTED
    → REJECTED

else if blocking_issue_count > 0
    → REJECTED

else if Privacy == CRITICAL
    → REJECTED

else if Privacy == HIGH
    → REVIEW_REQUIRED

else if Trust Score < 70
    → REVIEW_REQUIRED

else if Privacy == MEDIUM
    → REVIEW_REQUIRED

else
    → APPROVED
```

This means a score above `70` alone is not enough.

Example:

```text
Trust Score = 92
Privacy = HIGH

→ REVIEW_REQUIRED
```

Another example:

```text
Trust Score = 95
Validation = REJECTED

→ REJECTED
```

This is intentional.

The system models trust as a governed decision rather than a single scalar score.

---

## 22. Promotion Eligibility

Governance approval and lifecycle state are both required for promotion.

The final promotion condition is:

```text
lifecycle_state == VALIDATED
AND
governance decision exists
AND
decision == APPROVED
AND
promotion_eligible == True
```

Only then can a version move to:

```text
ACTIVE
```

This prevents the project from treating a high score as automatic authorization.

---

## 23. What Drift Does

Drift Detection is another evidence stream.

It compares:

```text
baseline dataset
vs
current dataset
```

The current project can inspect:

```text
Schema Drift
Numeric Drift
Categorical Distribution Drift
PSI
KS-test evidence
```

Drift is currently not one of the five weighted Trust Score components.

That separation is useful because drift is inherently comparative:

```text
current data relative to baseline
```

while the current Trust Score primarily evaluates one dataset snapshot.

---

## 24. What Freshness Does

Freshness asks:

```text
How old is the newest ingestion?
```

It compares ingestion age against:

```text
max_age_minutes
```

Typical states are:

```text
FRESH
STALE
NO_DATA
```

Freshness is not included in the Data Trust Score.

It belongs to operational observability.

A technically clean dataset can still be stale.

---

## 25. What Volume Monitoring Does

Volume Monitoring asks:

```text
Did the newest ingestion contain an unusual number of rows
relative to the previous ingestion?
```

Typical states are:

```text
NORMAL
DROP
SPIKE
NO_BASELINE
```

Volume Monitoring is also not part of the current Trust Score.

A dataset can have a high Trust Score while its ingestion volume suddenly drops.

That is why operational monitoring remains separate.

---

## 26. What Data Contracts Do

Data Contracts describe expected schema-level compatibility.

They can define:

```text
column name
expected type
required/not required
nullable/not nullable
```

Current logical contract types include:

```text
NUMERIC
CATEGORICAL
DATETIME
BOOLEAN
TEXT
```

A contract result can be:

```text
COMPATIBLE
BREAKING
```

Enforcement can be:

```text
BLOCK
WARN
```

Data Contract compatibility is not numerically folded into the current Trust Score.

It acts as its own gate in the governed workflow.

---

## 27. Why the Platform Uses Multiple Signals

A single score cannot answer all of these questions:

```text
Is the data complete?
Are values valid?
Are rows duplicated?
Are values anomalous?
Does it contain PII?
Did its schema change?
Is it stale?
Did the row count collapse?
Did governance approve it?
```

Therefore the architecture intentionally uses several layers.

```text
Quality evidence
      ↓
Trust Score

Privacy evidence
      ↓
Governance

Validation evidence
      ↓
Governance

Trust Score
      ↓
Governance

Governance + Lifecycle
      ↓
Promotion

Freshness / Volume / Pipeline Events
      ↓
Operational Observability
```

## 28. Example Calculation

Suppose the component scores are:

```text
Completeness   = 95
Validity       = 90
Uniqueness     = 98
Consistency    = 92
Anomaly Safety = 80
```

The overall score is:

```text
95 × 0.25 = 23.75
90 × 0.25 = 22.50
98 × 0.20 = 19.60
92 × 0.15 = 13.80
80 × 0.15 = 12.00
```

Therefore:

```text
Overall
= 23.75 + 22.50 + 19.60 + 13.80 + 12.00
= 91.65
```

The Trust Score classification becomes:

```text
Risk Level = Low
AI Readiness = Ready for Analytics and ML
```

But Governance still evaluates Validation and Privacy separately.

If Privacy is:

```text
HIGH
```

then the final governance decision is:

```text
REVIEW_REQUIRED
```

despite the `91.65` Trust Score.

---

## 29. Another Example: Quality Failure

Suppose:

```text
Trust Score = 88
Privacy = LOW
Validation = REJECTED
blocking issues = 1
```

Governance returns:

```text
REJECTED
```

The high Trust Score does not override a blocking validation failure.

This is one of the most important architectural points in the project.

## 30. API Consistency

The score API creates a DataFrame from submitted records and then calls:

```text
run_quality_checks(...)
```

followed by:

```text
calculate_data_trust_score(...)
```

The API therefore exposes the same core scoring engine instead of copying formulas into route code.

This makes the scoring implementation easier to test and evolve.

## 31. Persistence

When the user saves a full scan, the platform can persist:

```text
dataset metadata
scan run
quality issues
Trust Score
risk level
AI readiness
```

to SQL Server.

Persisted history allows later APIs and dashboards to inspect previous runs instead of depending only on Streamlit session state.

## 32. Rule-grounded AI Assistant

The assistant does not calculate a separate hidden Trust Score.

It receives scan context and explains the evidence already produced by the platform.

Relevant context can include:

```text
Trust Score
Quality Issues
Anomaly Detection
Privacy Risk
Drift
```

If the required context is missing, the assistant asks the user to run the relevant analysis rather than inventing a result.

This is why the assistant is described as:

```text
rule-grounded
```

rather than an autonomous scoring authority.

---

## 33. What the Score Is Not

The Data Trust Score is not:

```text
a probability that data is correct
a regulatory compliance score
a production SLA
a model-accuracy estimate
a security score
a substitute for domain validation
```

It is a deterministic portfolio metric for combining several measurable data-quality dimensions.

That limitation should be stated clearly in technical discussions.

---

## 34. Current Strengths of the Method

The current approach has several engineering advantages.

It is:

```text
deterministic
explainable
testable
bounded to 0-100
component-based
shared across API/UI/core
separate from governance
```

Each final score can be decomposed into its component contributions.

That is preferable to presenting an unexplained number.

---

## 35. Current Limitations

The scoring model is intentionally simple enough to remain understandable.

Current limitations include:

- weights are hand-defined rather than statistically learned,
- validity rules are heuristic and project-specific,
- duplicate detection is based on complete-row duplication,
- anomaly thresholds are generic defaults,
- Isolation Forest contamination defaults to `0.1`,
- domain-specific business rules are limited,
- Drift is not currently included in the weighted score,
- Privacy is not included in the weighted score,
- Freshness and Volume are operational signals rather than score components,
- AI Readiness is a rule-based interpretation rather than an empirical ML-readiness benchmark.

These are reasonable boundaries for the current prototype and also provide obvious future extension points.

## 37. Interview Explanation

A concise explanation for an interview is:

> The platform does not use one opaque quality number. It calculates a deterministic Data Trust Score from completeness, validity, uniqueness, consistency, and anomaly safety. Privacy, Data Contracts, Freshness, Volume Monitoring, and Drift remain separate evidence streams. Governance then combines technical validation, Trust Score, and Privacy Risk before a dataset is allowed to become promotion-eligible.

If asked why Privacy is separate:

> A dataset can be very clean but still contain sensitive PII, so quality and privacy should not be treated as the same property.

If asked why Governance is separate:

> A score summarizes evidence; governance makes the policy decision.

## 40. Summary

The current scoring architecture can be summarized as:

```text
Dataset
  │
  ├── Quality Rules
  │      │
  │      ├── Completeness
  │      ├── Validity
  │      ├── Uniqueness
  │      └── Consistency
  │
  ├── Anomaly Detection
  │      ├── IQR
  │      ├── Z-score
  │      └── Isolation Forest
  │
  └───────────────┐
                  ▼
          Data Trust Score
                  │
                  ├──────────────┐
                  │              │
            Validation       Privacy
                  │              │
                  └──────┬───────┘
                         ▼
                   Governance
                         │
                         ▼
               Promotion Eligibility
```

The key idea is simple:

```text
score summarizes evidence
governance decides what may happen next
observability watches what happens over time
```
